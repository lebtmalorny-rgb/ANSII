# Как проверять рекомендации ANSSI в OpenStack

Практическая методика для OpenStack 2025.1 Epoxy и Kolla-Ansible. Основание — руководство ANSSI-BP-104 v1.0 от 16.04.2024 и процитированная в нём редакция SecNumCloud v3.2. Номера страниц далее относятся к печатной нумерации французского оригинала. Методика описывает ожидаемые результаты. Проверки на инфраструктуре пользователя не выполнялись.

## Где в документах описаны проверки

| Источник | Что в нём можно взять для проверки |
|---|---|
| ANSSI-BP-104, §1.1 и главы 2–6 | Формулировку меры, защищаемую границу и привязку к требованиям SecNumCloud. ANSSI отдельно указывает, что детальная настройка зависит от способа развёртывания. Для большинства рекомендаций нет готовой процедуры с командами и критерием приёмки. |
| ANSSI-BP-104, приложение A.2.1 и A.2.2, стр. 59–74 | Примеры источников событий, настроек и реальных форматов сообщений. Например, показан отказ аутентификации Keystone и пара сообщений Audit Middleware для запроса к Nova. По ним можно определить, какие поля искать в собственном журнале. |
| Nova, источник [41], редакция Epoxy | Есть подразделы проверки среды TLS на вычислительных узлах, проверка прав на файлы PKI и шаг с пробной миграцией. Эти шаги дают техническую основу для R38/R39. |
| SecNumCloud v3.2, источник [9] | Условия, которые должен обеспечить поставщик, включая организационные и эксплуатационные меры. Информацию об удалении копий, управлении ключами или применяемой политике предоставляет владелец соответствующей системы. |
| Kolla-Ansible и руководства сервисов 2025.1 | Путь конфигурации, поддерживаемые опции и ограничения версии. Эти источники позволяют отделить предусмотренную возможность от защиты, реально действующей в конкретном облаке. |

Источники: [ANSSI-BP-104](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf) · [Nova 2025.1, проверка среды TLS](https://docs.openstack.org/nova/2025.1/admin/secure-live-migration-with-qemu-native-tls.html#validating-your-tls-environment-on-compute-nodes) · [Kolla-Ansible 2025.1, параметры сервисов](https://docs.openstack.org/kolla-ansible/2025.1/admin/advanced-configuration.html).

## Как принять одну рекомендацию

1. Запишите ID рекомендации, применимый сервис, версию, топологию и границу проверки. Например, «клиент → HAProxy» и «HAProxy → Glance API» — два разных соединения. Если сервис отсутствует, укажите, какую функцию он заменяет или почему сценарий не применяется.
2. Зафиксируйте намерение и действующую конфигурацию. Для Kolla проверьте заданные значения на deploy-узле и то, что видит процесс в работающем контейнере. Укажите узлы, которые действительно обслужили запрос.
3. Выполните обычную операцию тестовой учётной записью. При проверке разграничения используйте разрешённый и запрещённый случаи. В качестве исходной точки укажите конкретную сеть, контейнер или клиентский профиль. Для HSM, СХД, LDAP, сети и резервных копий можно использовать протокол владельца соответствующей системы с теми же сведениями о контуре и дате.
4. Сверьте фактическое решение с ожидаемым. Сохраните время в UTC, псевдоним теста, ID объекта или запроса, небольшой фрагмент результата и данные точки, принявшей решение. Перед передачей протокола удалите пароли, токены, ключи, заголовки авторизации и параметры запросов, содержащие секреты.

**Статусы.** «Подтверждено» — критерий выполнен по всему заявленному охвату. «Не выполнено» — наблюдение опровергает критерий. «Частично» — подтверждена только часть пути, узлов или условий. «Не проверено» — свидетельств пока нет. «Неприменимо» требует архитектурного обоснования. Если вместо меры ANSSI применяется другой механизм, запишите его как «Альтернативная мера» и отдельно зафиксируйте решение о её приёмке. Итог такой проверки относится к выбранной конфигурации и не присваивает квалификацию SecNumCloud.

## Три проверки, которые можно воспроизвести

### R4. Убедиться, что административный вход изолирован от сети заказчика

**Что даёт ANSSI.** В §2.2, стр. 19–20, сформулировано требование разделения сетей. Следующие действия и критерий — предлагаемый способ проверить его на развёрнутом облаке.

1. На бастионе с правом чтения каталога выполните команду ниже. Укажите в переменной REGION идентификатор региона и выберите активный сервис Identity. Выпишите опубликованные адреса. Если интерфейс типа admin не зарегистрирован, выясните, каким входом пользуется поставщик, по конфигурации HAProxy и сетевой схеме. Без этой информации проверке административного входа присваивают статус «Не проверено». [Справка CLI Epoxy](https://docs.openstack.org/python-openstackclient/2025.1/cli/command-objects/endpoint-v3.html#endpoint-list)

```bash
openstack --os-cloud auditor endpoint list --service identity --region "$REGION"
```

2. На рабочей станции в сети заказчика проверьте версионный URL Keystone внешнего входа. С удалённого административного клиента выполните ту же команду для разрешённого управляющего входа. Используйте реальные FQDN с корректными SAN и доверенным УЦ, URL включает путь версии Keystone, например `/v3/`. Подставьте значения переменных для каждого запуска. Для входа с обязательным mTLS используйте утверждённый тестовый профиль с его собственным сертификатом.

```bash
date -u '+%Y-%m-%dT%H:%M:%SZ'
curl --connect-timeout 5 --max-time 12 --cacert "$CA_FILE" \
  --silent --show-error --output /dev/null \
  --write-out 'peer=%{remote_ip} HTTP=%{http_code}\n' "$KEYSTONE_V3_URL"
```

3. С той же станции заказчика проверьте известный административный адрес, согласованный для теста. Сопоставьте время и адреса с правилами маршрутизации и событием запрета на границе. Проверьте, не повлияли ли на результат DNS, клиентский HTTP-прокси или отсутствующий доверенный УЦ.

**Успех.** Оба штатных пути работают, а для пути «заказчик → управляющий вход» подтверждены изоляция и точка запрета. Сохраните таблицу трёх направлений и соответствующие записи. Если HTTP 401 вернул сам управляющий API, запрос до него дошёл. Если ответ вернул входной прокси, его журнал покажет, был ли запрос передан дальше. Тайм-аут или ошибка DNS сами по себе не доказывают сетевую изоляцию. Повторите по остальным опубликованным сервисам и регионам.

### R39. Проверить защищённую горячую миграцию

**Что даёт Nova.** В источнике [41] описано, как запустить `virt-pki-validate` на обеих сторонах, проверить права на файлы PKI и выполнить миграцию. Наличие сертификата проверяет предпосылку. Успех переноса ВМ подтверждает работоспособность. Для приёмки шифрования нужны сведения о том, какой транспорт использовался. [Инструкция Nova 2025.1](https://docs.openstack.org/nova/2025.1/admin/secure-live-migration-with-qemu-native-tls.html).

1. Нужны два вычислительных узла и отдельная тестовая ВМ, допускающая горячую миграцию. На обоих узлах проверьте видимые реальным процессам Nova/libvirt/QEMU параметры и каталоги сертификатов. Для схемы из инструкции Nova проверьте `[libvirt] live_migration_with_native_tls = true` и `live_migration_scheme = tls`. Первый параметр относится к TLS переноса QEMU, второй — к управляющему соединению libvirt.
2. Выполните `virt-pki-validate` в окружении с фактической конфигурацией libvirt, если утилита поставлена и рассчитана на ваши пути. Для контейнерной установки проверьте монтирование PKI и права на файлы и каталоги внутри соответствующего контейнера. Не копируйте содержимое закрытых ключей в отчёт.
3. Выполните штатную горячую миграцию тестовой ВМ. Зафиксируйте ID миграции, время, исходный и целевой compute, состояние ВМ до и после. На этих узлах свяжите событие миграции с записью об установлении TLS для потока передачи данных. Сверьте версию TLS и набор шифров с действующим криптографическим профилем. При отсутствии этих полей укажите предел доказательства. Если используется перенос дисков по NBD, получите подтверждение и для этого потока. В схеме с shared storage для дискового потока укажите, что он не задействован.

**Успех.** ВМ продолжила работу на целевом узле, а для каждого задействованного канала имеется эксплуатационное подтверждение защиты. Если имеется только вывод `virt-pki-validate` и запись Nova об успешной миграции, пометьте доказательство шифрования потока как неполное.

### R50+. Проследить один запрос от CLI до централизованного журнала

**Что даёт ANSSI.** В A.2.2.2, стр. 66–71, приведены события `audit.http.request` и `audit.http.response` для запроса Nova. Поля включают исполнителя, `requestPath`, `initiator.request_id`, результат обработки и для ответа — `reason.reasonCode`. Ниже приведён тест именно варианта с Audit Middleware.

1. Выберите существующую тестовую ВМ и проектную учётную запись, имеющую право её просматривать. Зафиксируйте UUID ВМ и короткий интервал времени. Не включайте отладочный вывод CLI.

```bash
date -u '+%Y-%m-%dT%H:%M:%SZ'
openstack --os-cloud qa-project server show "$TEST_SERVER_ID" -f value -c id
printf 'CLI exit=%s\n' "$?"
date -u '+%Y-%m-%dT%H:%M:%SZ'
```

2. Оператор журналирования ищет в центральном хранилище события Nova по интервалу, исполнителю, проекту и пути, заканчивающемуся на `/servers/<UUID>`. В схеме исходного JSON путь хранится в `payload.requestPath`, идентификатор — `payload.initiator.request_id`. Индекс сборщика может развернуть эти поля. По ID найдите пару `audit.http.request` / `audit.http.response` одного обращения Nova. Если ID запроса не записан, используйте общий `payload.id` пары, предварительно сверив путь и окно времени. CLI может выполнить дополнительные обращения, в том числе к Keystone, с другими идентификаторами.
3. Сверьте ресурс, действие чтения, результат и время поступления. Для успешной пары ожидаются `pending` в запросе, `success` и код HTTP 200 в ответе. В примере ANSSI значения находятся в `payload.outcome` и `payload.reason.reasonCode`. HTTP-метод GET при необходимости подтверждают по журналу доступа. Зафиксируйте обезличенные поля двух событий и общий ID. Если получено только одно, проверьте включённый конвейер, карту API, исключения, транспорт и доставку до приёмника. Для транспорта через очередь локального файла события может не быть.

**Как трактовать отказ.** Для уже предусмотренного штатного теста отказа возьмите его протокол и выясните, какой компонент ответил. Если запрос дошёл до Nova через фильтр аудита, ищите в записи ответа фактический код, причину и результат обработки. Код 404 сам по себе не различает отсутствующий и скрытый политикой ресурс. При отказе на прокси или в `auth_token` до фильтра Audit Middleware пара Nova может отсутствовать. Тогда свидетельство берут на отказавшем компоненте. Отказ не подтверждает успешный путь чтения.

**Успех для данного запроса.** CLI завершился с кодом 0 и выдал запрошенный UUID, а приёмник сохранил соответствующие запрос и успешный ответ. Если по проекту для R50+ выбран журнал HTTP, достаточно одной записи доступа с методом, путём и кодом 200. Связь с тестом подтвердите записанным request ID либо однозначным сочетанием тестового UUID, времени и клиентского контекста. Такая запись подтверждает путь HTTP-журнала. Если для этого сервиса заявлен CADF, отдельно предъявляется пара событий CADF. Успех одного запроса подтверждает одну цепочку. Для итоговой отметки R50+ пройдите выбранный профиль по всем входящим в него сервисам и источникам. [Настройка Audit Middleware в Epoxy](https://docs.openstack.org/keystonemiddleware/2025.1/audit.html).

## Карточки приёмки по всем рекомендациям

В каждой карточке указан пункт ANSSI и его страница. Действия, критерии и набор свидетельств ниже — предлагаемый протокол проверки. Номера в квадратных скобках отсылают к тематически связанным позициям исходной библиографии. Выпуски Pike, Newton, Rocky и страницы latest нужно сверять с Epoxy. Варианты R50−, R50 и R50+ отражают разные уровни полноты журналирования.

### Доступ, каталоги и разграничение API

#### R1. Настроить Keystone на использование каталога LDAP

**Точка проверки и права.** Аудитор конфигурации Keystone и журнала тестовых входов LDAP

**Действие.** Проверить действующий драйвер домена, доверенную цепочку TLS до каталога и область поиска. Сопоставить свежие штатные сценарии для активной и отключённой тестовых записей.

**Критерий и свидетельство.** Активная запись проходит вход, отключённая — получает отказ при новой аутентификации. Из событий видно обращение к указанному LDAP. Сохранить имя домена, логическое имя каталога и результаты обеих проверок.

[ANSSI, стр. 16](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=18) · Материалы [[22]](https://docs.openstack.org/keystone/pike/admin/identity-integrate-with-ldap.html), [[20]](https://docs.openstack.org/keystone/latest/admin/configuration.html).

#### R2. Использовать несколько доменов и выделить для них отдельные каталоги LDAP

**Точка проверки и права.** Аудитор назначений Keystone и администратор каталогов с правом чтения настроек

**Действие.** Составить соответствие «домен → LDAP → группа → область роли». Отдельно проверить домен поставщика `Default` в архитектуре ANSSI, домены заказчиков и служебные идентификаторы. Сопоставить штатные тесты входа в свой и чужой домены.

**Критерий и свидетельство.** Поставщика и заказчиков обслуживают разные каталоги согласно схеме. Профиль каждого контура входит в свой домен и получает только предусмотренные назначения. Сохранить обезличенную таблицу, разрешённые и отклонённые решения.

[ANSSI, стр. 16](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=18) · Материалы [[20]](https://docs.openstack.org/keystone/latest/admin/configuration.html), [[22]](https://docs.openstack.org/keystone/pike/admin/identity-integrate-with-ldap.html), [[31]](https://docs.openstack.org/keystone/pike/admin/identity-concepts.html), [[32]](https://docs.openstack.org/security-guide/identity/policies.html).

#### R3. Использовать разные TCP-порты для точек доступа admin и public

**Точка проверки и права.** Аудитор каталога и активной конфигурации балансировщика, чтение списка сокетов

**Действие.** Для каждой опубликованной службы сопоставить внешний и административный входы по FQDN, адресу, TCP-порту и работающему обработчику. Сопоставить со штатными успешными обращениями к обоим входам.

**Критерий и свидетельство.** У каждой пары разные порты. Оба разрешённых маршрута обслуживаются ожидаемыми обработчиками. Сохранить пары портов, привязки и две записи доступа. Разные адреса с одинаковым портом оставляют буквальное требование R3 невыполненным.

[ANSSI, стр. 19](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=21) · Материалы [[18]](https://docs.openstack.org/kolla-ansible/latest/admin/advanced-configuration.html).

#### R4. Разместить API public и admin в разных сетях

**Точка проверки и права.** Сетевой аудитор с правом чтения схемы маршрутизации и ACL, точки наблюдения в двух зонах

**Действие.** Сверить привязки публичных, внутренних и административных адресов к сетям. По журналу межсетевого экрана проверить разрешённый доступ каждой зоны к своему сервису и решение для запрещённого направления из клиентской зоны.

**Критерий и свидетельство.** Публичная сеть отделена от внутренней и административной. Оба штатных направления работают, клиентский маршрут к закрытым адресам блокируется. Сохранить номера сетей, идентификаторы правил и результаты.

[ANSSI, стр. 20](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=22) · Материалы [[18]](https://docs.openstack.org/kolla-ansible/latest/admin/advanced-configuration.html).

#### R5. Установить обратный прокси-сервер перед API заказчиков

**Точка проверки и права.** Аудитор публичного DNS, прокси и входных ACL серверов API

**Действие.** Проверить, куда клиентский DNS разрешает имена API. По разрешённому запросу чтения сопоставить вход прокси и обработку API. По ACL и журналу решений проверить отсутствие доступного клиентам прямого пути до backend.

**Критерий и свидетельство.** Для всех публикуемых API разрешённый запрос проходит через прокси. Прямой доступ из клиентской сети закрыт. Свидетельства — реестр имён, адресов входа и правил, две связанные записи разрешённого запроса.

[ANSSI, стр. 20](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=22) · Материалы [[18]](https://docs.openstack.org/kolla-ansible/latest/admin/advanced-configuration.html), [[45]](https://docs.openstack.org/security-guide/api-endpoints/api-endpoint-configuration-recommendations.html).

#### R6. Настроить фильтрацию прикладного уровня перед API

**Точка проверки и права.** Аудитор активной политики WAF и её событий

**Действие.** Сверить охват всех открытых административных API заказчика и режим блокировки. Найти одобренный штатный запрос и предусмотренный приёмочным тестом безвредный запрос, отклонённый по конкретному правилу метода или пути.

**Критерий и свидетельство.** Первый запрос принят, второй заблокирован до приложения. Сохранить идентификаторы политики, правила, двух тестов и результат. Ответ 403 сам по себе не указывает, какой компонент отказал.

[ANSSI, стр. 22](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=24) · Материалы [[9]](https://cyber.gouv.fr/documents/388/secnumcloud-referentiel-exigences-v3.2.pdf), [[45]](https://docs.openstack.org/security-guide/api-endpoints/api-endpoint-configuration-recommendations.html).

#### R7. Блокировать токены admin при обращении к API заказчиков

**Точка проверки и права.** Аудитор политик и журналов решений публичного прокси

**Действие.** По результатам штатных тестов проверки происхождения сравнить две операции: собственный клиентский контур на публичном входе и проверочный сценарий чужого контура. Проверить, что правило покрывает все опубликованные входы.

**Критерий и свидетельство.** Свой контур разрешён, токен, выданный через вход поставщика, отклоняется публичным прокси до backend. Сохранить метки контура выдачи, входа и решения в двух тестах без значения токена.

[ANSSI, стр. 23](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=25) · Материалы [[30]](https://docs.openstack.org/keystone/pike/admin/identity-fernet-token-faq.html), [[19]](https://docs.openstack.org/keystone/pike/admin/identity-caching-layer.html).

#### R8. Блокировать токены public при обращении к API поставщика

**Точка проверки и права.** Аудитор внутреннего шлюза и политики доступа оператора

**Действие.** Проверить обратное направление отдельно на входах поставщика. Сверить тест штатного операторского пути и тест отклонения клиентского контура с журналом решения внутреннего шлюза.

**Критерий и свидетельство.** Операторский путь работает. Клиентский контур отклоняется и не передаётся в API. Сохранить пары «контур → вход», версию политики, UTC и решения. Проверка R7 не заменяет R8.

[ANSSI, стр. 24](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=26) · Материалы [[30]](https://docs.openstack.org/keystone/pike/admin/identity-fernet-token-faq.html), [[19]](https://docs.openstack.org/keystone/pike/admin/identity-caching-layer.html).

### Сертификаты и связь с удостоверением

#### R9. Настроить взаимную аутентификацию клиента OpenStack и прокси-сервера

**Точка проверки и права.** Аудитор входной TLS-конфигурации, тестовый клиент с собственным тестовым сертификатом

**Действие.** На том же FQDN и порту проверить обязательность клиентского сертификата, доверие к серверу и издателям клиентских сертификатов. Сопоставить TLS-события с сертификатом и без него.

**Критерий и свидетельство.** Соединение с соответствующим тестовым сертификатом достигает ожидаемого обработчика, отсутствие или недоверенный сертификат приводит к отказу на TLS-входе либо в обязательной проверке прокси до API. Сохранить имя входа, публичный отпечаток сертификата и причину решения.

#### R10. Проверять соответствие сертификата X.509 идентификатору пользователя

**Точка проверки и права.** Аудитор правил сопоставления шлюза, прав чтения достаточно для реестра тестовых идентификаторов

**Действие.** Проверить источник DN — сертификат, прошедший проверку, — и отображение в LDAP с учётом домена. Сверить штатные случаи совпадения и несовпадения для тестовых удостоверений.

**Критерий и свидетельство.** Совпадение разрешает продолжить аутентификацию. Несовпадение запрещает вход. Сохранить псевдонимы пользователей, версии правил и решения, включая запись LDAP для тестовой пары.

[ANSSI, стр. 28](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=30) · Материалы [[4]](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-recommandations_de_securite_relatives_a_tls-v1.2.pdf), [[22]](https://docs.openstack.org/keystone/pike/admin/identity-integrate-with-ldap.html).

#### R11. Сохранять соответствие между DN сертификата X.509 и токеном, выданным Keystone

**Точка проверки и права.** Аудитор конфигурации и телеметрии механизма привязки, без права читать значения кеша

**Действие.** Сверить схему записи «DN сертификата + хеш токена», место создания записи после выдачи и срок хранения. Сопоставить штатный тест успешной выдачи с событием регистрации, а тест отклонённой выдачи — с отсутствием регистрации и результатом отказа.

**Критерий и свидетельство.** Успешной выдаче соответствует одна действующая привязка с ожидаемым сроком. При отказе действующая привязка не возникает. Сохранить идентификаторы транзакций, агрегированные счётчики и события жизненного цикла; сами пары не выгружаются.

[ANSSI, стр. 29](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=31) · Материалы [[30]](https://docs.openstack.org/keystone/pike/admin/identity-fernet-token-faq.html).

#### R12. Проверять соответствие между токенами клиентов OpenStack и предъявленными сертификатами X.509

**Точка проверки и права.** Аудитор шлюза, политики отказа и журналов разрешённых/отклонённых обращений

**Действие.** Сверить штатные тесты совпадения, несовпадения и отсутствия записи, включая истёкшую привязку. Проверить охват каждого узла и защищённого входа.

**Критерий и свидетельство.** Запрос разрешается только при действующей паре. Несовпадение или отсутствие пары блокируется до сервисного API. Сохранить результаты проверок, причины решений и записи об успешной доставке штатного запроса.

[ANSSI, стр. 29](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=31) · Материалы [[30]](https://docs.openstack.org/keystone/pike/admin/identity-fernet-token-faq.html).

### Шифрование хранилищ и соединений

#### R13. Включить шифрование томов в Nova

**Исполнитель и действие.** Администратор Cinder с управляющего узла выполняет `openstack volume type show --encryption-type "$TYPE"` и `openstack volume show "$VOL"`. На compute или СХД владелец находит активный механизм шифрования именно этого тестового тома по UUID.

**Критерий и свидетельство.** Для профиля front-end результат содержит LUKS, ожидаемую длину ключа и `encrypted=True`. Есть сопоставление UUID с зашифрованным устройством или параметрами драйвера запущенной тестовой ВМ. Сохранить выписку без ключей. Для утверждения о всех томах требуется инвентаризация типов и фактических томов.

[ANSSI, стр. 32](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=34) · Материалы [[38]](https://docs.openstack.org/security-guide/tenant-data/data-encryption.html).

#### R14. Включить шифрование данных в хранилище Swift

**Исполнитель и действие.** Оператор Swift сверяет порядок `keymaster encryption` в рабочем proxy pipeline. Для свежего небольшого тестового объекта с известным содержимым оператор хранилища сверяет логический объект и именно его физическую запись в изолированной тестовой реплике.

**Критерий и свидетельство.** Штатное чтение API возвращает контрольные данные. На соответствующей записи подтверждены метаданные шифрования и зашифрованное представление. В протоколе — имя политики, идентификатор объекта и результат сверки. Имена объектов и контейнеров механизм Swift не шифрует.

[ANSSI, стр. 32](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=34) · Материалы [[49]](https://docs.openstack.org/swift/latest/overview_encryption.html).

#### R15. Включить шифрование трафика между Swift и Glance

**Исполнитель и действие.** При Swift store оператор выполняет штатное скачивание тестового образа через Glance. Сопоставляет запись Swift proxy с соединением **Glance → Swift**, в том числе после промежуточных прокси.

**Критерий и свидетельство.** По времени и объекту установлен фактический путь. На сетевых участках подтверждены TLS-сеансы и проверка УЦ клиентом. Сохранить обезличенные журналы обеих сторон. Для иного store указать отсутствие этого потока.

[ANSSI, стр. 32](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=34) · Материалы [[49]](https://docs.openstack.org/swift/latest/overview_encryption.html), [[46]](https://docs.openstack.org/security-guide/secure-communication/introduction-to-ssl-and-tls.html).

#### R16. Включить шифрование трафика между Glance и Nova

**Исполнитель и действие.** Администратор Nova берёт загрузку тестовой ВМ из образа, ранее отсутствовавшего в кеше compute. В журналах Nova, Glance и прокси находит GET тела этого образа и соответствующую TLS-сессию.

**Критерий и свидетельство.** Есть UUID образа, источники и назначения, ответ и параметры TLS для каждого фактического участка. Попадание в кеш или только GET метаданных не проверяет передачу содержимого. Для прямого доступа к хранилищу проверить его фактический протокол отдельно.

[ANSSI, стр. 32](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=34) · Материалы [[46]](https://docs.openstack.org/security-guide/secure-communication/introduction-to-ssl-and-tls.html).

#### R17. Защищать ключи шифрования

**Исполнитель и действие.** Ответственные за Barbican и PKI составляют перечень ключей шифрования данных и проверяют места хранения, права доступа, процедуру восстановления и журнал недавнего обращения.

**Критерий и свидетельство.** Для каждого класса ключей установлены хранитель, доступные операции и охват резервных копий. Представлены ACL и обезличенная запись использования. Для аппаратной защиты дополнительно нужны свидетельства R24 и R25.

[ANSSI, стр. 33](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=35) · Материалы [[6]](https://cyber.gouv.fr/documents/339/RGS_v-2-0_B2.pdf), [[44]](https://docs.openstack.org/security-guide/secrets-management/secrets-management-use-cases.html).

#### R18. Настроить TLS для API служб OpenStack в соответствии с современными требованиями безопасности

**Исполнитель и действие.** Оператор составляет список активных API и VIP через `openstack endpoint list`. Из клиентской сети проверяет каждый адрес, например `openssl s_client -connect "$HOST:$PORT" -servername "$HOST" -verify_hostname "$HOST" -verify_return_error -CAfile "$CA" </dev/null` для DNS-имени.

**Критерий и свидетельство.** Для каждого адреса — успешная проверка цепочки и имени, версия TLS, согласованный шифр и настройка listener с разрешёнными протоколами по принятому профилю. Backend-участки проверены отдельно из сети прокси. Одна успешная сессия не подтверждает запрет устаревших версий.

[ANSSI, стр. 34](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=36) · Материалы [[4]](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-recommandations_de_securite_relatives_a_tls-v1.2.pdf), [[45]](https://docs.openstack.org/security-guide/api-endpoints/api-endpoint-configuration-recommendations.html), [[46]](https://docs.openstack.org/security-guide/secure-communication/introduction-to-ssl-and-tls.html).

#### R19. Настроить TLS с взаимной аутентификацией для службы очередей сообщений

**Исполнитель и действие.** Оператор RabbitMQ на брокере сопоставляет реальные подключения служб по `rabbitmqctl list_connections user ssl ssl_protocol peer_cert_subject`. На тестовом listener или по ранее оформленному протоколу испытаний проверяет отказ без клиентского сертификата при действующих остальных реквизитах.

**Критерий и свидетельство.** Для всех охваченных клиентов TLS активен, виден ожидаемый сертификат и сервер требует его предъявления. TLS с паролем даёт частичное выполнение. Сохранить сводку по клиентам и ответ на контрольную попытку. Штатное ограничение Kolla указано выше.

[ANSSI, стр. 35](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=37) · Материалы [[4]](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-recommandations_de_securite_relatives_a_tls-v1.2.pdf), [[39]](https://docs.openstack.org/oslo.messaging/latest/configuration/opts.html), [[43]](https://docs.openstack.org/security-guide/messaging/security.html).

#### R20. Настроить TLS с взаимной аутентификацией для службы базы данных

**Исполнитель и действие.** DBA проверяет отдельно соединения служба → ProxySQL и ProxySQL → MariaDB. Для тестового SQL-сеанса по TCP фиксирует статус TLS на соответствующем конце, например `SHOW SESSION STATUS LIKE 'Ssl_cipher'` непосредственно в MariaDB. Проверяет правила обязательного предъявления клиентского сертификата и результат соединения без него.

**Критерий и свидетельство.** Для каждого участка есть подтверждение проверки сервера клиентом, предъявления клиентского сертификата и отказа без него. Поле `Ssl_cipher` доказывает шифрование только наблюдаемого SQL-сеанса. Приложить раздельный протокол двух участков и список охваченных клиентов.

[ANSSI, стр. 35](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=37) · Материалы [[4]](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-recommandations_de_securite_relatives_a_tls-v1.2.pdf), [[23]](https://mariadb.com/docs/server/security/encryption/data-in-transit-encryption/securing-connections-for-client-and-server), [[42]](https://docs.openstack.org/security-guide/databases/database-transport-security.html).

#### R21. Организовать туннели IPsec между кешем токенов и службами OpenStack

**Исполнитель и действие.** Администратор сети сопоставляет все пары клиент–Memcached с IPsec-политиками. Во время штатной тестовой операции с кешем проверяет изменение счётчиков соответствующей ассоциации безопасности в IKE/IPsec и отсутствие обходного открытого маршрута.

**Критерий и свидетельство.** Для каждого используемого пути есть идентификатор пары и изменение счётчика. При защите TLS вместо требуемого в R21 IPsec зафиксировать эквивалент, клиентский backend, проверку УЦ и действующий TLS-сеанс. Решение о признании эквивалентности принимает владелец требований.

[ANSSI, стр. 35](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=37) · Материалы [[3]](https://messervices.cyber.gouv.fr/documents-guides/NT_IPsec.pdf), [[19]](https://docs.openstack.org/keystone/pike/admin/identity-caching-layer.html).

#### R22. Настроить Glance на использование Cinder

**Исполнитель и действие.** Администраторы Glance и Cinder проверяют текущие `enabled_backends`, `default_backend`, фактический store нового тестового образа и соответствующий том-носитель на стороне Cinder.

**Критерий и свидетельство.** Конкретный образ помещён в Cinder store, извлечение проходит, том-носитель опознан. В протоколе — идентификаторы и store. В multistore указать охват остальных маршрутов. Другой backend оформить как архитектурное отличие.

[ANSSI, стр. 36](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=38) · Материалы [[37]](https://docs.openstack.org/cinder/latest/admin/blockstorage-volume-backed-image.html).

#### R23. Настроить TLS для Glance

**Исполнитель и действие.** Оператор API проверяет фактическое подключение к Glance API через VIP, затем к backend из сети HAProxy с правильным именем серверного сертификата. Сопоставляет обращение к тестовому образу с access log.

### Управление секретами и HSM

#### R24. Настроить Barbican на использование HSM

**Исполнитель и действие.** Оператор Barbican и хранитель HSM сопоставляют выбранный для тестового проекта secret store и PKCS#11 plugin с операцией над обезличенным тестовым секретом. На стороне HSM находят событие или изменение счётчика соответствующей операции в выделенном интервале.

**Критерий и свидетельство.** Опознаны фактические модуль/слот и обслужившая запрос HSM-сессия. У тестового проекта не использован программный store. При интерпретации журнала учтено кеширование ключей. Сохранить идентификаторы операции и журнал HSM без секретных атрибутов.

[ANSSI, стр. 37](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=39) · Материалы [[44]](https://docs.openstack.org/security-guide/secrets-management/secrets-management-use-cases.html), [[48]](https://messervices.cyber.gouv.fr/visas/ANSSI-CC-2016-07-rapport.pdf).

#### R25. Использовать HSM, прошедший сертификацию безопасности

**Исполнитель и действие.** Аудитор сверяет производителя, модель, аппаратную ревизию, прошивку, режим работы установленного HSM и область действия сертификата безопасности по реестру органа сертификации.

**Критерий и свидетельство.** Совпадают продукт, версии и режим, документ принят в рамках требований проекта. Приложить номер сертификата, дату проверки и обезличенную инвентарную карточку. Наличие PKCS#11 само по себе не подтверждает сертификацию.

[ANSSI, стр. 37](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=39) · Материалы [[48]](https://messervices.cyber.gouv.fr/visas/ANSSI-CC-2016-07-rapport.pdf).

#### R26. Ограничить доступ к секретам средствами управления доступом Barbican

**Исполнитель и действие.** Владелец тестового секрета получает `openstack acl get "$SECRET_URI"`. Разрешённый и исключённый из ACL тестовые пользователи штатно запрашивают операцию чтения контрольного секрета. Полученные тестовые данные не сохраняют.

**Критерий и свидетельство.** Результаты соответствуют ACL, членству и фактической политике. Есть успешный ответ и отказ для той же операции над тем же URI. Проверка только метаданных недостаточна, если оценивается доступ к содержимому.

[ANSSI, стр. 37](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=39) · Материалы [[32]](https://docs.openstack.org/security-guide/identity/policies.html), [[44]](https://docs.openstack.org/security-guide/secrets-management/secrets-management-use-cases.html).

#### R27. Разрешить доступ к HSM только с машин, на которых работает Barbican

**Исполнитель и действие.** Сетевой администратор и хранитель HSM сверяют адреса Barbican, правила доступа к прикладному интерфейсу HSM и журналы соединений. В тестовой сети подтверждают допуск с разрешённого узла и отказ с известного постороннего тестового узла.

**Критерий и свидетельство.** Есть список разрешённых инициаторов, результат контрольного соединения с каждой стороны и соответствующее правило. Управление HSM и резервирование описаны отдельно от прикладного доступа.

[ANSSI, стр. 38](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=40) · Материалы [[44]](https://docs.openstack.org/security-guide/secrets-management/secrets-management-use-cases.html), [[48]](https://messervices.cyber.gouv.fr/visas/ANSSI-CC-2016-07-rapport.pdf).

#### R28. Внедрить процедуры автоматизации жизненного цикла секретов

**Исполнитель и действие.** Оператор процесса выбирает тестовый секрет с коротким сроком и прослеживает в обычном расписании создание, наступление срока, обработку и последующую сверку. Использует идентификатор задания и метаданные.

**Критерий и свидетельство.** Автоматизация действительно выполнила предусмотренные политикой действия, оставила статус и корректно обработала повторный запуск. Одно поле expiration подтверждает лишь метаданные.

[ANSSI, стр. 38](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=40) · Материалы [[6]](https://cyber.gouv.fr/documents/339/RGS_v-2-0_B2.pdf), [[44]](https://docs.openstack.org/security-guide/secrets-management/secrets-management-use-cases.html).

#### R29. Предоставить заказчикам процедуры аудита прав доступа к секретам и управления этими правами

**Исполнитель и действие.** Администратору заказчика выдают его штатную процедуру. На тестовом проекте он формирует список разрешённых субъектов и их прав, изменяет разрешение тестовой записи и повторяет проверку.

**Критерий и свидетельство.** В выгрузке учтены роли проекта и явные ACL. По результатам штатных запросов видно, что право изменилось только у нужного субъекта. Сохранить отчёты до/после и ссылку на версию процедуры.

[ANSSI, стр. 39](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=41) · Материалы [[32]](https://docs.openstack.org/security-guide/identity/policies.html), [[44]](https://docs.openstack.org/security-guide/secrets-management/secrets-management-use-cases.html).

#### R30. Регистрировать обращения к секретам

**Исполнитель и действие.** Пользователь выполняет чтение тестового секрета и получает контролируемый отказ для второго тестового пользователя. Оператор находит соответствующие события в центральном аудите.

**Критерий и свидетельство.** По времени, субъекту, операции, объекту и коду результата видны обе попытки. Сохранить две записи с корреляционным идентификатором при наличии. Проверить отсутствие значения секрета и токена в выгрузке.

[ANSSI, стр. 39](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=41) · Материалы [[5]](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-recommandations_securite_architecture_systeme_journalisation.pdf), [[44]](https://docs.openstack.org/security-guide/secrets-management/secrets-management-use-cases.html).

#### R31. Предоставить заказчикам процедуры стирания секретов

**Исполнитель и действие.** Заказчик выполняет штатную процедуру удаления отдельного тестового секрета без потребителей либо предъявляет протокол такой проверки. Владелец резервного копирования предоставляет сроки и механизм работы с копиями.

**Критерий и свидетельство.** После удаления повторный штатный запрос к исходному URI не возвращает секрет. Сохранить событие и результат запроса. Отдельно зафиксировать сроки уничтожения копий и доказательство криптостирания, если оно заявлено.

[ANSSI, стр. 39](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=41) · Материалы [[6]](https://cyber.gouv.fr/documents/339/RGS_v-2-0_B2.pdf), [[44]](https://docs.openstack.org/security-guide/secrets-management/secrets-management-use-cases.html).

### Изоляция зависимостей, ресурсов и сетей

#### R32. Выделить отдельные службы баз данных для разных компонентов

**Исполнитель и действие.** DBA сопоставляет каждую службу с фактическим экземпляром или кластером БД. Сверяет привязку за ProxySQL по runtime-топологии и учёт подключения на конкретном кластере.

**Критерий и свидетельство.** Для разных компонентов выделены разные серверы или кластеры в смысле R32. Разные схемы на одном кластере отмечены как частичное выполнение. Сохранить таблицу «служба → узлы БД» и идентификаторы кластеров без DSN и паролей.

[ANSSI, стр. 40](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=42) · Материалы [[9]](https://cyber.gouv.fr/documents/388/secnumcloud-referentiel-exigences-v3.2.pdf), [[42]](https://docs.openstack.org/security-guide/databases/database-transport-security.html).

#### R33. Выделить отдельные службы кеширования для разных компонентов

**Исполнитель и действие.** Оператор кеша сводит адреса, которыми реально пользуется каждая служба, с инвентарём серверов/кластеров кеша и наблюдаемыми клиентами.

**Критерий и свидетельство.** Разные компоненты используют выделенные серверы/кластеры. Разные ключевые префиксы в одном Memcached не выполняют буквальную рекомендацию. Приложить карту серверов и клиентов.

[ANSSI, стр. 41](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=43) · Материалы [[9]](https://cyber.gouv.fr/documents/388/secnumcloud-referentiel-exigences-v3.2.pdf), [[19]](https://docs.openstack.org/keystone/pike/admin/identity-caching-layer.html).

#### R34. Выделить сеть для сторонних служб

**Исполнитель и действие.** Сетевой администратор сверяет интерфейсы и сети данных, кеша, брокера, маршруты и применённые ACL. Во время штатной операции проверяет путь по локальной телеметрии или журналу межсетевого экрана.

**Критерий и свидетельство.** Для перечисленных служб выделены сети, доступ ограничен необходимыми инициаторами. Сохранить таблицу потоков, VLAN/VRF или подсети и запись разрешённого соединения.

[ANSSI, стр. 41](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=43) · Материалы [[9]](https://cyber.gouv.fr/documents/388/secnumcloud-referentiel-exigences-v3.2.pdf), [[42]](https://docs.openstack.org/security-guide/databases/database-transport-security.html), [[43]](https://docs.openstack.org/security-guide/messaging/security.html).

#### R35. Выделить отдельные сети для отдельных видов сторонних служб

**Исполнитель и действие.** Администратор HA устанавливает фактический транспорт Corosync и других сторонних служб, использующих multicast. Для каждого проверяет сеть интерфейса и область доставки.

**Критерий и свидетельство.** Multicast ограничен выделенной сетью, что подтверждено конфигурацией и телеметрией. Если используются только unicast-транспорты, представить их конфигурацию и указать неприменимость именно этого пункта.

[ANSSI, стр. 41](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=43) · Материалы [[9]](https://cyber.gouv.fr/documents/388/secnumcloud-referentiel-exigences-v3.2.pdf).

#### R36. Обеспечить возможность создания выделенных агрегатов вычислительных узлов для отдельных заказчиков

**Исполнитель и действие.** Администратор Nova сверяет `openstack aggregate show "$AGG"`, фактический состав узлов и соответствующий aggregate в Placement. Проверяет размещение тестовых ВМ A и B по обычному пути планировщика.

**Критерий и свидетельство.** Узлы выделенной группы принимают только разрешённые проекты, а экземпляры проекта с обязательной привязкой попадают на допустимые узлы. Для изоляции через Placement UUID и состав совпадают с Nova. Сохранить правила и результаты по обеим сторонам границы.

[ANSSI, стр. 43](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=45) · Материалы [[25]](https://docs.openstack.org/newton/config-reference/compute/schedulers.html).

#### R37. Предложить заказчикам типы виртуальных машин, привязанные к агрегатам вычислительных узлов

**Исполнитель и действие.** Администратор сравнивает `openstack flavor show "$FLAVOR"`, extra specs, доступность типа и метаданные агрегата. Владелец проекта создаёт небольшую тестовую ВМ с этим типом, администратор проверяет фактический хост.

**Критерий и свидетельство.** Тип выбирается нужным проектом и ведёт в предназначенный агрегат. Для обязательной изоляции проверены также доступные заказчику альтернативные типы. Приложить UUID типа, ВМ и агрегата.

[ANSSI, стр. 43](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=45) · Материалы [[25]](https://docs.openstack.org/newton/config-reference/compute/schedulers.html).

#### R38. Настроить горячую миграцию виртуальных машин средствами QEMU

**Исполнитель и действие.** Администратор выполняет или наблюдает плановую горячую миграцию только тестовой ВМ между двумя подготовленными узлами. Проверяет историю операции Nova и транспорт переноса данных в libvirt/QEMU на обоих узлах.

**Критерий и свидетельство.** Зафиксирована успешная передача памяти средствами QEMU. Указаны исходный и целевой узлы, ID миграции, сохранение работы тестовой ВМ и фактический транспорт. Успех операции сам по себе не идентифицирует транспорт. Служебные SSH-соединения проверяются по назначению.

[ANSSI, стр. 44](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=46) · Материалы [[40]](https://docs.openstack.org/nova/latest/admin/configuring-migrations.html), [[41]](https://docs.openstack.org/nova/latest/admin/secure-live-migration-with-qemu-native-tls.html).

#### R39. Настроить в QEMU современное TLS-шифрование трафика миграции виртуальных машин

**Исполнитель и действие.** При той же миграции проверяют эффективные настройки Nova и QEMU, доступность цепочек сертификатов на обоих узлах и TLS для реального потока переноса памяти. Для поддерживаемой block migration проверяют также канал NBD.

**Критерий и свидетельство.** Зафиксированы проверка сертификатов, защищённый канал управления libvirt и отдельно TLS на передаче данных. Протокол только для shared storage не доказывает проверку дискового канала. Сохранить параметры и корреляцию потоков миграции.

[ANSSI, стр. 44](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=46) · Материалы [[4]](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-recommandations_de_securite_relatives_a_tls-v1.2.pdf), [[40]](https://docs.openstack.org/nova/latest/admin/configuring-migrations.html), [[41]](https://docs.openstack.org/nova/latest/admin/secure-live-migration-with-qemu-native-tls.html).

#### R40. Настроить в Swift несколько наборов хранилищ

**Исполнитель и действие.** Оператор Swift сопоставляет активные storage policies из `swift.conf` с object rings и списками устройств. Для тестового объекта проверяет политику контейнера и соответствующие устройствам кольца места размещения.

**Критерий и свидетельство.** Используется несколько объектных колец. Если заявлена физическая изоляция, списки устройств и их идентификаторы подтверждают нужное разделение. Сохранить индекс политики и обезличенные списки устройств.

[ANSSI, стр. 45](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=47) · Материалы [[28]](https://docs.openstack.org/swift/latest/overview_policies.html).

#### R41. Сопоставить каждому набору хранилищ отдельную подсистему Cinder

**Исполнитель и действие.** Администраторы Cinder и Swift сопоставляют каждое кольцо с конкретным backend/пулом по проектной схеме, инвентарю устройств, драйверу Cinder и действующей конфигурации.

**Критерий и свидетельство.** Прямая связь подтверждена документацией конкретной архитектуры и образцами размещения. Upstream описывает отдельные механизмы Swift и Cinder; совпадение имён не создаёт связи. Без реализации этого варианта указать альтернативу и основание для её приёмки.

[ANSSI, стр. 45](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=47) · Материалы [[28]](https://docs.openstack.org/swift/latest/overview_policies.html), [[36]](https://docs.openstack.org/cinder/rocky/configuration/block-storage/config-options.html).

#### R42. Ограничить доступ проектов к подсистемам хранения с помощью квот Cinder

**Исполнитель и действие.** Администратор собирает правила private types, `volume_backend_name`, квоты по типам обоих тестовых проектов и список публичных типов. Проверяет разрешённый и запрещённый сценарии через обычный API на тестовых ресурсах.

**Критерий и свидетельство.** Разрешённый том попадает в ожидаемый пул, создание через запрещённый тип отклонено. Учитываются другой публичный тип с тем же backend и тип по умолчанию. Если защита построена исключительно на видимости private types, отметить отличие от исходного варианта с квотами.

[ANSSI, стр. 45](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=47) · Материалы [[36]](https://docs.openstack.org/cinder/rocky/configuration/block-storage/config-options.html).

#### R43+. Настроить Neutron на инкапсуляцию трафика между вычислительными узлами в туннели IPsec

**Исполнитель и действие.** Оператор сети сверяет используемый datapath, пары VTEP и политики IPsec. Между двумя тестовыми ВМ на разных compute запускает небольшой разрешённый обмен. На обоих концах наблюдает IKE/IPsec-состояние, рост защищённых счётчиков и телеметрию физического интерфейса.

**Критерий и свидетельство.** Для фактической пары VTEP есть активные ассоциации безопасности, ESP либо его согласованная UDP-инкапсуляция и учтённый трафик. Контролируется отсутствие разрешённого обходного открытого пути. Один только VLAN/VXLAN/Geneve подтверждает сегментацию. Материалы OVS описывают технологию и не гарантируют её включение в Kolla.

[ANSSI, стр. 46](https://messervices.cyber.gouv.fr/documents-guides/anssi-guide-openstack_v1-0.pdf#page=48) · Материалы [[3]](https://messervices.cyber.gouv.fr/documents-guides/NT_IPsec.pdf), [[34]](https://docs.openvswitch.org/en/latest/howto/ipsec/).

#### R44. Внедрить политику периодической смены мастер-ключей HSM

**Критерий и свидетельство.** Запись исчезла из обслуживающих копий. Есть подтверждение удаления или документированный срок исчезновения из резервных копий с проверкой восстановления. Отсутствие объекта в Keystone подтверждает только уровень API. При внешнем LDAP указать ответственного владельца.

#### R46. Использовать модуль безопасности Linux (LSM)

**Исполнитель и действие.** На compute администратор проверяет действующий LSM. Для SELinux выполняет `getenforce`, смотрит метки процессов двух контрольных ВМ и связанных дисков, а также фактические security labels в libvirt.

**Критерий и свидетельство.** При использовании sVirt действует Enforcing, контексты гостевых процессов и ресурсов соответствуют политике и позволяют различать две ВМ. Одного статуса Enforcing на хосте недостаточно. Сохранить только согласованные метки. Для другого LSM предъявить сопоставимое подтверждение.

**Критерий и свидетельство.** Пользователь `guest` удалён, административные и прикладные права разделены, опубликован перечень разрешённых ресурсов и тем. Есть успешная и отклонённая операция в границах политики. Ограничение configure/write/read и ограничение routing key проверены отдельно.

## Где настраивать в Epoxy

### Доступ к API и журналирование в Epoxy

**R1–R2. Где проходит граница LDAP.** При файловой конфигурации Keystone включает отдельные драйверы параметром `[identity] domain_specific_drivers_enabled = true` и читает `/etc/keystone/domains/keystone.<имя_домена>.conf` внутри контейнера. В доменном файле задаются `[identity] driver = ldap`, доверенный сервер и параметры поиска пользователей и групп. Keystone читает пользователей и группы из LDAP, а назначения ролей хранит в SQL. В исходной схеме ANSSI для операторов домена `Default` выделен каталог поставщика, для доменов заказчиков используются другие каталоги. До перехода действующего `Default` составьте перечень сервисных и аварийных учётных записей и их доменов. Замена драйвера существующего домена не переносит пользователей в LDAP. [Keystone 2025.1 — Domain-specific configuration и LDAP](https://docs.openstack.org/keystone/2025.1/admin/configuration.html#domain-specific-configuration)

**R3–R8. Где применяется запрет.** В Kolla схема с раздельными сетями задаётся через `kolla_internal_vip_address`, `network_interface`, `kolla_external_vip_address` и `kolla_external_vip_interface`. В варианте с раздельными VIP внешняя точка получает отдельный адрес, а внутренняя и административная могут использовать один. Порты входных обработчиков сравнивают отдельно. Каталог Keystone сообщает клиенту URL. Метка `admin`, `internal` или `public` сама по себе не ограничивает операции и не закрепляет токен за входом. Проследите маршрут до экземпляра API, сетевые ACL, правила WAF и место принятия решения о допустимом контуре выдачи токена. В R7/R8 термин «токен admin/public» обозначает контур выдачи в схеме руководства. Роль пользователя и тип интерфейса в каталоге — независимые признаки. [Kolla 2025.1 — сети конечных точек и overrides](https://docs.openstack.org/kolla-ansible/2025.1/admin/advanced-configuration.html) · [Keystone 2025.1 — каталог](https://docs.openstack.org/keystone/2025.1/admin/manage-services.html#service-catalog)

**R9–R12. Как доказать связь сертификата с пользователем.** Шифрование клиентского соединения до VIP и шифрование соединения HAProxy с API настраивают независимо. Обязательную проверку клиентского сертификата, сопоставление DN с пользователем LDAP и привязку к хешу токена проверяют как отдельные функции выбранного входного шлюза. Вариант с федерацией и MFA на внешнем IdP может решать другую задачу — подтверждение нескольких факторов при входе. Для буквального выполнения R11/R12 понадобятся свидетельства регистрации и проверки связки именно для последующих обращений к API. Kolla также поддерживает федерацию Keystone, а сам Keystone позволяет задавать правила MFA индивидуально, например сочетание пароля и TOTP. [Kolla 2025.1 — TLS](https://docs.openstack.org/kolla-ansible/2025.1/admin/tls.html) · [Kolla 2025.1 — федерация](https://docs.openstack.org/kolla-ansible/2025.1/reference/shared-services/keystone-guide.html#federated-identity) · [Keystone 2025.1 — MFA](https://docs.openstack.org/keystone/2025.1/admin/multi-factor-authentication.html)

**R48–R50. Что нужно включить.** Часы и Linux Audit проверяют на хосте. Для журналов приложений проверяют полную цепочку от события в сервисе до поиска на сервере сбора. Обычный параметр `node_custom_config` указывает на `/etc/kolla/config` на узле развёртывания. Например, следующий фрагмент для `keystone.conf` подходит, если действующая схема направляет уведомления в очередь и там уже настроен получатель. Значения других драйверов, от которых зависят телеметрия и учёт, нужно сохранить.

```ini
[DEFAULT]
notification_format = cadf
notification_opt_out = identity.authenticate.pending

[oslo_messaging_notifications]
driver = messagingv2
```

В приведённом варианте исключены только промежуточные события. В образце upstream Epoxy по умолчанию указаны исключения и для `success`, и для `pending`. Для успешного и неуспешного входа проверьте фактический `outcome` на стороне получателя. [Keystone 2025.1 — параметры уведомлений](https://docs.openstack.org/keystone/2025.1/configuration/samples/keystone-conf.html) · [Keystone 2025.1 — формат и события](https://docs.openstack.org/keystone/2025.1/admin/event_notifications.html)

Для Horizon Kolla принимает файл `/etc/kolla/config/horizon/_9999-custom-settings.py`. Актуальные имена опций — `OPERATION_LOG_ENABLED` и `OPERATION_LOG_OPTIONS`. Пример включает журнал и перечисляет поля, необходимые для разбора, без записи содержимого параметров формы. Дополнительно нужен действующий обработчик Python logging, который принимает журнал операций и передаёт его сборщику. Для регистрации обращений к API, исключённых из Horizon, проверяйте собственные журналы соответствующих сервисов.

```python
OPERATION_LOG_ENABLED = True
OPERATION_LOG_OPTIONS = {
    "target_methods": ["GET", "POST", "PUT", "DELETE"],
    "ignored_urls": ["/js/", "/static/"],
    "mask_fields": ["password", "current_password", "original_password",
                    "new_password", "confirm_password", "secret", "token"],
    "format": ("[%(domain_id)s] [%(project_id)s] [%(user_id)s] "
               "[%(client_ip)s] [%(method)s] [%(http_status)s]"),
}
```

В примере опущен путь. Для восстановления конкретной операции дополните схему безопасным идентификатором действия или связывайте запись с очищенным журналом HTTP по запросу, времени и контексту. При выборе полей с URL учитывайте их строки запроса. [Horizon 2025.1 — журнал операций](https://docs.openstack.org/horizon/2025.1/configuration/settings.html#operation-log-enabled) · [Kolla 2025.1 — настройки Horizon](https://docs.openstack.org/kolla-ansible/2025.1/reference/shared-services/horizon-guide.html)

Для CADF-аудита HTTP нужно включить фильтр `keystonemiddleware.audit:filter_factory` в активном WSGI-конвейере после `auth_token` и предоставить карту API конкретного сервиса (`audit_map_file`). Драйвер `[audit_middleware_notifications] driver = log` позволяет отправить аудит в журнал при сохранении отдельного транспорта обычных уведомлений. У разных сервисов разные конвейеры и способы доставки файлов. В Kolla для общего сбора журналов предусмотрены `enable_central_logging` и дополнительные входы, фильтры и выходы Fluentd. Включение общего сбора само по себе не включает источники аудита в приложениях. [Audit Middleware 2025.1](https://docs.openstack.org/keystonemiddleware/2025.1/audit.html) · [Kolla 2025.1 — центральное журналирование](https://docs.openstack.org/kolla-ansible/2025.1/reference/logging-and-monitoring/central-logging-guide.html)

### Хранилища, TLS и вычислительные узлы

- **Хранилища.** Для фронтального шифрования Cinder задаёт тип тома с провайдером `luks` и `control_location=front-end`. Nova и Cinder должны использовать совместимый менеджер ключей, например Barbican. Тип применяется при создании тома. Уже существующие тома, локальные диски и образы учитывают отдельно. Glance поддерживает выбор хранилищ через `enabled_backends` и `[glance_store] default_backend`. Cinder и Swift — разные возможные хранилища образов. Укажите, какой маршрут используется фактически. [Cinder, шифрование томов](https://docs.openstack.org/cinder/2025.1/configuration/block-storage/volume-encryption.html) · [Glance, хранилища](https://docs.openstack.org/glance/2025.1/admin/multistores.html) · [Swift, шифрование объектов](https://docs.openstack.org/swift/2025.1/overview_encryption.html)
- **TLS на API.** При раздельных внутренних и внешних VIP за соединения клиентов с HAProxy отвечают `kolla_enable_tls_internal` и `kolla_enable_tls_external`. За соединения HAProxy с поддерживаемыми API отвечает `kolla_enable_tls_backend`. Если сеть одна, документация Kolla предусматривает настройку через внутренние переменные. Сертификаты должны соответствовать именам или IP, к которым действительно подключаются клиенты. Доверенный корпоративный УЦ должен быть доступен всем участникам. [Kolla-Ansible 2025.1, TLS](https://docs.openstack.org/kolla-ansible/2025.1/admin/tls.html)
- **Очереди, БД и кеш.** В Kolla настройка `rabbitmq_enable_tls` защищает поддерживаемый клиентский канал. В документации ветки 2025.1 указано отсутствие штатной поддержки клиентских сертификатов для этого канала. Для БД в типовой установке ветки присутствует ProxySQL, поэтому нужно учесть два соединения. В отличие от ситуации, описанной ANSSI, в Epoxy библиотека `oslo.cache` предоставляет `[cache] tls_enabled` и `tls_cafile` для совместимых backend. Применимость проверяют отдельно для каждого клиента, в том числе middleware проверки токенов. Переход на TLS вместо IPsec фиксируют как иной способ защиты. [RabbitMQ в Kolla](https://docs.openstack.org/kolla-ansible/2025.1/reference/message-queues/rabbitmq.html) · [ProxySQL](https://docs.openstack.org/kolla-ansible/2025.1/admin/proxysql.html) · [oslo.cache](https://docs.openstack.org/oslo.cache/2025.1/configuration/)
- **Контейнеры и миграция.** Управляемые настройки служб задают на узле развёртывания в `node_custom_config` (обычно `/etc/kolla/config`). Например, файл `/etc/kolla/config/nova/nova-scheduler.conf` относится к планировщику. Поддерживаемые пути определяет роль установленной версии. Для libvirt Kolla документирует `libvirt_tls` и отдельные сертификаты узлов. Для native TLS руководство Nova указывает `[libvirt] live_migration_with_native_tls=true`, `live_migration_scheme=tls`, PKI на обоих compute, параметры проверки сертификата в `qemu.conf` и несовместимость с `live_migration_tunnelled=true`. Сначала сверьте сформированные настройки и версию роли, чтобы не дублировать их вручную. [Настройки Kolla](https://docs.openstack.org/kolla-ansible/2025.1/admin/advanced-configuration.html) · [Libvirt в Kolla](https://docs.openstack.org/kolla-ansible/2025.1/reference/compute/libvirt-guide.html) · [Native TLS в Nova](https://docs.openstack.org/nova/2025.1/admin/secure-live-migration-with-qemu-native-tls.html)

Для R36 через Placement проверьте в действующем конфиге планировщика параметр `[scheduler] limit_tenants_to_placement_aggregate`. При его включении режим `placement_aggregate_required_for_tenants=true` требует соответствующего агрегата для каждого планируемого проекта. Перед применением такого режима следует найти проекты без сопоставления, иначе их заявки на новые ВМ останутся без подходящего узла. Ограничение доступа других проектов к выделенному узлу подтверждают отдельным сценарием. Администратор может прочитать фактический хост контрольной ВМ командой `openstack server show "$VM" -c OS-EXT-SRV-ATTR:host -f value` при доступном расширенном поле. [Параметры Nova 2025.1](https://docs.openstack.org/nova/2025.1/configuration/config.html)

Связи между агрегатами Nova и Placement, расчёт пула Cinder и назначение object ring описаны независимо друг от друга. Для эксплуатационных команд RabbitMQ, OVS и libvirt приведена документация их разработчиков. Она не привязана к версии OpenStack, поэтому параметры сверяют с поставленной версией. [Агрегаты Nova](https://docs.openstack.org/nova/2025.1/admin/aggregates.html) · [Пулы Cinder](https://docs.openstack.org/cinder/2025.1/admin/multi-backend.html) · [Политики Swift](https://docs.openstack.org/swift/2025.1/overview_policies.html) · [IPsec в OVS](https://docs.openvswitch.org/en/latest/tutorials/ipsec/) · [Изоляция QEMU в libvirt](https://libvirt.org/drvqemu.html) · [Права RabbitMQ](https://www.rabbitmq.com/docs/access-control) · [CLI RabbitMQ](https://www.rabbitmq.com/docs/cli)

### Команды для сбора свидетельств

**Примеры сбора сведений без изменения конфигурации.** Имена облачного профиля и сервиса заменяют на локальные. Используйте профиль аудитора с правами чтения соответствующих API. Имя файла TLS-ключа ниже относится только к сертификату тестового клиента. В качестве URL укажите согласованный маршрут чтения, на котором действует проверяемый профиль mTLS.

```bash
openstack --os-cloud auditor endpoint list --service identity
openstack --os-cloud auditor domain list
openstack --os-cloud auditor role assignment list --user "$TEST_USER_ID" --names --effective
ss -lnt
getent ahosts "$PUBLIC_FQDN"
chronyc tracking
chronyc -n sources -v
sudo auditctl -s
sudo auditctl -l
```

```bash
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  --cacert "$SERVER_CA" --cert "$TEST_CERT" --key "$TEST_KEY" "$TEST_URL"
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  --cacert "$SERVER_CA" "$TEST_URL"
```

Успешная TLS-проверка и успешная авторизация на прикладном уровне — разные наблюдения. Для R9 зафиксируйте отдельно статус TLS, код HTTP, если он получен, и решение публичного шлюза. Код `000` у curl означает, что клиент не получил HTTP-ответа. Причину уточняют по коду завершения и журналу шлюза. Для R49 чтение конкретного файла можно зарегистрировать без вывода его содержимого, например `sudo head -c 1 "$CONFIG_PATH" > /dev/null`; запись ищут по штатному изменению, уже проведённому в том же наблюдаемом расположении. [chrony — команды мониторинга](https://chrony-project.org/doc/4.6/chronyc.html) · [Red Hat Enterprise Linux 9 — Linux Audit](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/security_hardening/auditing-the-system_security-hardening)
