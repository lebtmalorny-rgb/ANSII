Как проверять рекомендации ANSSI в OpenStack

Практическая методика для OpenStack 2025.1 Epoxy и Kolla-Ansible. Основание — руководство ANSSI-BP-104 v1.0 от 16.04.2024 и процитированная в нём редакция SecNumCloud v3.2. Номера страниц далее относятся к печатной нумерации французского оригинала. Методика описывает ожидаемые результаты. Проверки на инфраструктуре пользователя не выполнялись.

Как принять одну рекомендацию

  1. Запишите ID рекомендации, применимый сервис, версию, топологию и границу проверки. Например, «клиент → HAProxy» и «HAProxy → Glance API» — два разных соединения. Если сервис отсутствует, укажите, какую функцию он заменяет или почему сценарий не применяется.
  2. Зафиксируйте намерение и действующую конфигурацию. Для Kolla проверьте заданные значения на deploy-узле и то, что видит процесс в работающем контейнере. Укажите узлы, которые действительно обслужили запрос.
  3. Выполните обычную операцию тестовой учётной записью. При проверке разграничения используйте разрешённый и запрещённый случаи. В качестве исходной точки укажите конкретную сеть, контейнер или клиентский профиль. Для HSM, СХД, LDAP, сети и резервных копий можно использовать протокол владельца соответствующей системы с теми же сведениями о контуре и дате.
  4. Сверьте фактическое решение с ожидаемым. Сохраните время в UTC, псевдоним теста, ID объекта или запроса, небольшой фрагмент результата и данные точки, принявшей решение. Перед передачей протокола удалите пароли, токены, ключи, заголовки авторизации и параметры запросов, содержащие секреты.

Статусы. «Подтверждено» — критерий выполнен по всему заявленному охвату. «Не выполнено» — наблюдение опровергает критерий. «Частично» — подтверждена только часть пути, узлов или условий. «Не проверено» — свидетельств пока нет. «Неприменимо» требует архитектурного обоснования. Если вместо меры ANSSI применяется другой механизм, запишите его как «Альтернативная мера» и отдельно зафиксируйте решение о её приёмке. Итог такой проверки относится к выбранной конфигурации и не присваивает квалификацию SecNumCloud.

Три проверки, которые можно воспроизвести

R4. Убедиться, что административный вход изолирован от сети заказчика

Что даёт ANSSI. В §2.2, стр. 19–20, сформулировано требование разделения сетей. Следующие действия и критерий — предлагаемый способ проверить его на развёрнутом облаке.

  1. На бастионе с правом чтения каталога выполните команду ниже. Укажите в переменной REGION идентификатор региона и выберите активный сервис Identity. Выпишите опубликованные адреса. Если интерфейс типа admin не зарегистрирован, выясните, каким входом пользуется поставщик, по конфигурации HAProxy и сетевой схеме. Без этой информации проверке административного входа присваивают статус «Не проверено». Справка CLI Epoxy
openstack --os-cloud auditor endpoint list --service identity --region "$REGION"
  1. На рабочей станции в сети заказчика проверьте версионный URL Keystone внешнего входа. С удалённого административного клиента выполните ту же команду для разрешённого управляющего входа. Используйте реальные FQDN с корректными SAN и доверенным УЦ, URL включает путь версии Keystone, например /v3/. Подставьте значения переменных для каждого запуска. Для входа с обязательным mTLS используйте утверждённый тестовый профиль с его собственным сертификатом.
date -u '+%Y-%m-%dT%H:%M:%SZ'
curl --connect-timeout 5 --max-time 12 --cacert "$CA_FILE" \
  --silent --show-error --output /dev/null \
  --write-out 'peer=%{remote_ip} HTTP=%{http_code}\n' "$KEYSTONE_V3_URL"
  1. С той же станции заказчика проверьте известный административный адрес, согласованный для теста. Сопоставьте время и адреса с правилами маршрутизации и событием запрета на границе. Проверьте, не повлияли ли на результат DNS, клиентский HTTP-прокси или отсутствующий доверенный УЦ.

Успех. Оба штатных пути работают, а для пути «заказчик → управляющий вход» подтверждены изоляция и точка запрета. Сохраните таблицу трёх направлений и соответствующие записи. Если HTTP 401 вернул сам управляющий API, запрос до него дошёл. Если ответ вернул входной прокси, его журнал покажет, был ли запрос передан дальше. Тайм-аут или ошибка DNS сами по себе не доказывают сетевую изоляцию. Повторите по остальным опубликованным сервисам и регионам.

R39. Проверить защищённую горячую миграцию

Что даёт Nova. В источнике [41] описано, как запустить virt-pki-validate на обеих сторонах, проверить права на файлы PKI и выполнить миграцию. Наличие сертификата проверяет предпосылку. Успех переноса ВМ подтверждает работоспособность. Для приёмки шифрования нужны сведения о том, какой транспорт использовался. Инструкция Nova 2025.1.

  1. Нужны два вычислительных узла и отдельная тестовая ВМ, допускающая горячую миграцию. На обоих узлах проверьте видимые реальным процессам Nova/libvirt/QEMU параметры и каталоги сертификатов. Для схемы из инструкции Nova проверьте [libvirt] live_migration_with_native_tls = true и live_migration_scheme = tls. Первый параметр относится к TLS переноса QEMU, второй — к управляющему соединению libvirt.
  2. Выполните virt-pki-validate в окружении с фактической конфигурацией libvirt, если утилита поставлена и рассчитана на ваши пути. Для контейнерной установки проверьте монтирование PKI и права на файлы и каталоги внутри соответствующего контейнера. Не копируйте содержимое закрытых ключей в отчёт.
  3. Выполните штатную горячую миграцию тестовой ВМ. Зафиксируйте ID миграции, время, исходный и целевой compute, состояние ВМ до и после. На этих узлах свяжите событие миграции с записью об установлении TLS для потока передачи данных. Сверьте версию TLS и набор шифров с действующим криптографическим профилем. При отсутствии этих полей укажите предел доказательства. Если используется перенос дисков по NBD, получите подтверждение и для этого потока. В схеме с shared storage для дискового потока укажите, что он не задействован.

Успех. ВМ продолжила работу на целевом узле, а для каждого задействованного канала имеется эксплуатационное подтверждение защиты. Если имеется только вывод virt-pki-validate и запись Nova об успешной миграции, пометьте доказательство шифрования потока как неполное.

R50+. Проследить один запрос от CLI до централизованного журнала

Что даёт ANSSI. В A.2.2.2, стр. 66–71, приведены события audit.http.request и audit.http.response для запроса Nova. Поля включают исполнителя, requestPath, initiator.request_id, результат обработки и для ответа — reason.reasonCode. Ниже приведён тест именно варианта с Audit Middleware.

  1. Выберите существующую тестовую ВМ и проектную учётную запись, имеющую право её просматривать. Зафиксируйте UUID ВМ и короткий интервал времени. Не включайте отладочный вывод CLI.
date -u '+%Y-%m-%dT%H:%M:%SZ'
openstack --os-cloud qa-project server show "$TEST_SERVER_ID" -f value -c id
printf 'CLI exit=%s\n' "$?"
date -u '+%Y-%m-%dT%H:%M:%SZ'
  1. Оператор журналирования ищет в центральном хранилище события Nova по интервалу, исполнителю, проекту и пути, заканчивающемуся на /servers/<UUID>. В схеме исходного JSON путь хранится в payload.requestPath, идентификатор — payload.initiator.request_id. Индекс сборщика может развернуть эти поля. По ID найдите пару audit.http.request / audit.http.response одного обращения Nova. Если ID запроса не записан, используйте общий payload.id пары, предварительно сверив путь и окно времени. CLI может выполнить дополнительные обращения, в том числе к Keystone, с другими идентификаторами.
  2. Сверьте ресурс, действие чтения, результат и время поступления. Для успешной пары ожидаются pending в запросе, success и код HTTP 200 в ответе. В примере ANSSI значения находятся в payload.outcome и payload.reason.reasonCode. HTTP-метод GET при необходимости подтверждают по журналу доступа. Зафиксируйте обезличенные поля двух событий и общий ID. Если получено только одно, проверьте включённый конвейер, карту API, исключения, транспорт и доставку до приёмника. Для транспорта через очередь локального файла события может не быть.

Как трактовать отказ. Для уже предусмотренного штатного теста отказа возьмите его протокол и выясните, какой компонент ответил. Если запрос дошёл до Nova через фильтр аудита, ищите в записи ответа фактический код, причину и результат обработки. Код 404 сам по себе не различает отсутствующий и скрытый политикой ресурс. При отказе на прокси или в auth_token до фильтра Audit Middleware пара Nova может отсутствовать. Тогда свидетельство берут на отказавшем компоненте. Отказ не подтверждает успешный путь чтения.

Успех для данного запроса. CLI завершился с кодом 0 и выдал запрошенный UUID, а приёмник сохранил соответствующие запрос и успешный ответ. Если по проекту для R50+ выбран журнал HTTP, достаточно одной записи доступа с методом, путём и кодом 200. Связь с тестом подтвердите записанным request ID либо однозначным сочетанием тестового UUID, времени и клиентского контекста. Такая запись подтверждает путь HTTP-журнала. Если для этого сервиса заявлен CADF, отдельно предъявляется пара событий CADF. Успех одного запроса подтверждает одну цепочку. Для итоговой отметки R50+ пройдите выбранный профиль по всем входящим в него сервисам и источникам. Настройка Audit Middleware в Epoxy.

Карточки приёмки по всем рекомендациям

В каждой карточке указан пункт ANSSI и его страница. Действия, критерии и набор свидетельств ниже — предлагаемый протокол проверки. Номера в квадратных скобках отсылают к тематически связанным позициям исходной библиографии. Выпуски Pike, Newton, Rocky и страницы latest нужно сверять с Epoxy. Варианты R50−, R50 и R50+ отражают разные уровни полноты журналирования.

Доступ, каталоги и разграничение API

R1. Настроить Keystone на использование каталога LDAP

Точка проверки и права. Аудитор конфигурации Keystone и журнала тестовых входов LDAP

Действие. Проверить действующий драйвер домена, доверенную цепочку TLS до каталога и область поиска. Сопоставить свежие штатные сценарии для активной и отключённой тестовых записей.

Критерий и свидетельство. Активная запись проходит вход, отключённая — получает отказ при новой аутентификации. Из событий видно обращение к указанному LDAP. Сохранить имя домена, логическое имя каталога и результаты обеих проверок.

ANSSI, стр. 16 · Материалы [22], [20].

R2. Использовать несколько доменов и выделить для них отдельные каталоги LDAP

Точка проверки и права. Аудитор назначений Keystone и администратор каталогов с правом чтения настроек

Действие. Составить соответствие «домен → LDAP → группа → область роли». Отдельно проверить домен поставщика Default в архитектуре ANSSI, домены заказчиков и служебные идентификаторы. Сопоставить штатные тесты входа в свой и чужой домены.

Критерий и свидетельство. Поставщика и заказчиков обслуживают разные каталоги согласно схеме. Профиль каждого контура входит в свой домен и получает только предусмотренные назначения. Сохранить обезличенную таблицу, разрешённые и отклонённые решения.

ANSSI, стр. 16 · Материалы [20], [22], [31], [32].

R3. Использовать разные TCP-порты для точек доступа admin и public

Точка проверки и права. Аудитор каталога и активной конфигурации балансировщика, чтение списка сокетов

Действие. Для каждой опубликованной службы сопоставить внешний и административный входы по FQDN, адресу, TCP-порту и работающему обработчику. Сопоставить со штатными успешными обращениями к обоим входам.

Критерий и свидетельство. У каждой пары разные порты. Оба разрешённых маршрута обслуживаются ожидаемыми обработчиками. Сохранить пары портов, привязки и две записи доступа. Разные адреса с одинаковым портом оставляют буквальное требование R3 невыполненным.

ANSSI, стр. 19 · Материалы [18].

R4. Разместить API public и admin в разных сетях

Точка проверки и права. Сетевой аудитор с правом чтения схемы маршрутизации и ACL, точки наблюдения в двух зонах

Действие. Сверить привязки публичных, внутренних и административных адресов к сетям. По журналу межсетевого экрана проверить разрешённый доступ каждой зоны к своему сервису и решение для запрещённого направления из клиентской зоны.

Критерий и свидетельство. Публичная сеть отделена от внутренней и административной. Оба штатных направления работают, клиентский маршрут к закрытым адресам блокируется. Сохранить номера сетей, идентификаторы правил и результаты.

ANSSI, стр. 20 · Материалы [18].

R5. Установить обратный прокси-сервер перед API заказчиков

Точка проверки и права. Аудитор публичного DNS, прокси и входных ACL серверов API

Действие. Проверить, куда клиентский DNS разрешает имена API. По разрешённому запросу чтения сопоставить вход прокси и обработку API. По ACL и журналу решений проверить отсутствие доступного клиентам прямого пути до backend.

Критерий и свидетельство. Для всех публикуемых API разрешённый запрос проходит через прокси. Прямой доступ из клиентской сети закрыт. Свидетельства — реестр имён, адресов входа и правил, две связанные записи разрешённого запроса.

ANSSI, стр. 20 · Материалы [18], [45].

R6. Настроить фильтрацию прикладного уровня перед API

Точка проверки и права. Аудитор активной политики WAF и её событий

Действие. Сверить охват всех открытых административных API заказчика и режим блокировки. Найти одобренный штатный запрос и предусмотренный приёмочным тестом безвредный запрос, отклонённый по конкретному правилу метода или пути.

Критерий и свидетельство. Первый запрос принят, второй заблокирован до приложения. Сохранить идентификаторы политики, правила, двух тестов и результат. Ответ 403 сам по себе не указывает, какой компонент отказал.

ANSSI, стр. 22 · Материалы [9], [45].

R7. Блокировать токены admin при обращении к API заказчиков

Точка проверки и права. Аудитор политик и журналов решений публичного прокси

Действие. По результатам штатных тестов проверки происхождения сравнить две операции: собственный клиентский контур на публичном входе и проверочный сценарий чужого контура. Проверить, что правило покрывает все опубликованные входы.

Критерий и свидетельство. Свой контур разрешён, токен, выданный через вход поставщика, отклоняется публичным прокси до backend. Сохранить метки контура выдачи, входа и решения в двух тестах без значения токена.

ANSSI, стр. 23 · Материалы [30], [19].

R8. Блокировать токены public при обращении к API поставщика

Точка проверки и права. Аудитор внутреннего шлюза и политики доступа оператора

Действие. Проверить обратное направление отдельно на входах поставщика. Сверить тест штатного операторского пути и тест отклонения клиентского контура с журналом решения внутреннего шлюза.

Критерий и свидетельство. Операторский путь работает. Клиентский контур отклоняется и не передаётся в API. Сохранить пары «контур → вход», версию политики, UTC и решения. Проверка R7 не заменяет R8.

ANSSI, стр. 24 · Материалы [30], [19].

Сертификаты и связь с удостоверением

R9. Настроить взаимную аутентификацию клиента OpenStack и прокси-сервера

Точка проверки и права. Аудитор входной TLS-конфигурации, тестовый клиент с собственным тестовым сертификатом

Действие. На том же FQDN и порту проверить обязательность клиентского сертификата, доверие к серверу и издателям клиентских сертификатов. Сопоставить TLS-события с сертификатом и без него.

Доступ к API и журналирование в Epoxy

R1–R2. Где проходит граница LDAP. При файловой конфигурации Keystone включает отдельные драйверы параметром [identity] domain_specific_drivers_enabled = true и читает /etc/keystone/domains/keystone.<имя_домена>.conf внутри контейнера. В доменном файле задаются [identity] driver = ldap, доверенный сервер и параметры поиска пользователей и групп. Keystone читает пользователей и группы из LDAP, а назначения ролей хранит в SQL. В исходной схеме ANSSI для операторов домена Default выделен каталог поставщика, для доменов заказчиков используются другие каталоги. До перехода действующего Default составьте перечень сервисных и аварийных учётных записей и их доменов. Замена драйвера существующего домена не переносит пользователей в LDAP. Keystone 2025.1 — Domain-specific configuration и LDAP

R3–R8. Где применяется запрет. В Kolla схема с раздельными сетями задаётся через kolla_internal_vip_address, network_interface, kolla_external_vip_address и kolla_external_vip_interface. В варианте с раздельными VIP внешняя точка получает отдельный адрес, а внутренняя и административная могут использовать один. Порты входных обработчиков сравнивают отдельно. Каталог Keystone сообщает клиенту URL. Метка admin, internal или public сама по себе не ограничивает операции и не закрепляет токен за входом. Проследите маршрут до экземпляра API, сетевые ACL, правила WAF и место принятия решения о допустимом контуре выдачи токена. В R7/R8 термин «токен admin/public» обозначает контур выдачи в схеме руководства. Роль пользователя и тип интерфейса в каталоге — независимые признаки. Kolla 2025.1 — сети конечных точек и overrides · Keystone 2025.1 — каталог

R9–R12. Как доказать связь сертификата с пользователем. Шифрование клиентского соединения до VIP и шифрование соединения HAProxy с API настраивают независимо. Обязательную проверку клиентского сертификата, сопоставление DN с пользователем LDAP и привязку к хешу токена проверяют как отдельные функции выбранного входного шлюза. Вариант с федерацией и MFA на внешнем IdP может решать другую задачу — подтверждение нескольких факторов при входе. Для буквального выполнения R11/R12 понадобятся свидетельства регистрации и проверки связки именно для последующих обращений к API. Kolla также поддерживает федерацию Keystone, а сам Keystone позволяет задавать правила MFA индивидуально, например сочетание пароля и TOTP. Kolla 2025.1 — TLS · Kolla 2025.1 — федерация · Keystone 2025.1 — MFA

R48–R50. Что нужно включить. Часы и Linux Audit проверяют на хосте. Для журналов приложений проверяют полную цепочку от события в сервисе до поиска на сервере сбора. Обычный параметр node_custom_config указывает на /etc/kolla/config на узле развёртывания. Например, следующий фрагмент для keystone.conf подходит, если действующая схема направляет уведомления в очередь и там уже настроен получатель. Для успешного и неуспешного входа проверьте фактический outcome на стороне получателя. Keystone 2025.1 — параметры уведомлений · Keystone 2025.1 — формат и события

Для Horizon Kolla принимает файл /etc/kolla/config/horizon/_9999-custom-settings.py. Актуальные имена опций — OPERATION_LOG_ENABLED и OPERATION_LOG_OPTIONS. Пример включает журнал и перечисляет поля, необходимые для разбора, без записи содержимого параметров формы. Дополнительно нужен действующий обработчик Python logging, который принимает журнал операций и передаёт его сборщику. Для регистрации обращений к API, исключённых из Horizon, проверяйте собственные журналы соответствующих сервисов.

OPERATION_LOG_ENABLED = True
OPERATION_LOG_OPTIONS = {
    "target_methods": ["GET", "POST", "PUT", "DELETE"],
    "ignored_urls": ["/js/", "/static/"],
    "mask_fields": ["password", "current_password", "original_password",
                    "new_password", "confirm_password", "secret", "token"],
    "format": ("[%(domain_id)s] [%(project_id)s] [%(user_id)s] "
               "[%(client_ip)s] [%(method)s] [%(http_status)s]"),

В примере опущен путь. Для восстановления конкретной операции дополните схему безопасным идентификатором действия или связывайте запись с очищенным журналом HTTP по запросу, времени и контексту. Для CADF-аудита HTTP нужно включить фильтр keystonemiddleware.audit:filter_factory в активном WSGI-конвейере после auth_token и предоставить карту API конкретного сервиса (audit_map_file). Драйвер [audit_middleware_notifications] driver = log позволяет отправить аудит в журнал при сохранении отдельного транспорта обычных уведомлений. Хранилища, TLS и вычислительные узлы

  • Хранилища. Для фронтального шифрования Cinder задаёт тип тома с провайдером luks и control_location=front-end. Nova и Cinder должны использовать совместимый менеджер ключей, например Barbican. Тип применяется при создании тома. Уже существующие тома, локальные диски и образы учитывают отдельно. Glance поддерживает выбор хранилищ через enabled_backends и [glance_store] default_backend. Cinder и Swift — разные возможные хранилища образов. Укажите, какой маршрут используется фактически. Cinder, шифрование томов · Glance, хранилища · Swift, шифрование объектов
  • TLS на API. При раздельных внутренних и внешних VIP за соединения клиентов с HAProxy отвечают kolla_enable_tls_internal и kolla_enable_tls_external. За соединения HAProxy с поддерживаемыми API отвечает kolla_enable_tls_backend. Если сеть одна, документация Kolla предусматривает настройку через внутренние переменные. Сертификаты должны соответствовать именам или IP, к которым действительно подключаются клиенты. Доверенный корпоративный УЦ должен быть доступен всем участникам. Kolla-Ansible 2025.1, TLS
  • Очереди, БД и кеш. В Kolla настройка rabbitmq_enable_tls защищает поддерживаемый клиентский канал. В документации ветки 2025.1 указано отсутствие штатной поддержки клиентских сертификатов для этого канала. Для БД в типовой установке ветки присутствует ProxySQL, поэтому нужно учесть два соединения. В отличие от ситуации, описанной ANSSI, в Epoxy библиотека oslo.cache предоставляет [cache] tls_enabled и tls_cafile для совместимых backend. Применимость проверяют отдельно для каждого клиента, в том числе middleware проверки токенов. Переход на TLS вместо IPsec фиксируют как иной способ защиты. RabbitMQ в Kolla · ProxySQL · oslo.cache
  • Контейнеры и миграция. Управляемые настройки служб задают на узле развёртывания в node_custom_config (обычно /etc/kolla/config). Например, файл /etc/kolla/config/nova/nova-scheduler.conf относится к планировщику. Поддерживаемые пути определяет роль установленной версии. Для libvirt Kolla документирует libvirt_tls и отдельные сертификаты узлов. Для native TLS руководство Nova указывает [libvirt] live_migration_with_native_tls=true, live_migration_scheme=tls, PKI на обоих compute, параметры проверки сертификата в qemu.conf и несовместимость с live_migration_tunnelled=true. Сначала сверьте сформированные настройки и версию роли, чтобы не дублировать их вручную. Настройки Kolla · Libvirt в Kolla · Native TLS в Nova

Для R36 через Placement проверьте в действующем конфиге планировщика параметр [scheduler] limit_tenants_to_placement_aggregate. При его включении режим placement_aggregate_required_for_tenants=true требует соответствующего агрегата для каждого планируемого проекта. Перед применением такого режима следует найти проекты без сопоставления, иначе их заявки на новые ВМ останутся без подходящего узла. Ограничение доступа других проектов к выделенному узлу подтверждают отдельным сценарием. Администратор может прочитать фактический хост контрольной ВМ командой openstack server show "$VM" -c OS-EXT-SRV-ATTR:host -f value при доступном расширенном поле. Параметры Nova 2025.1

Связи между агрегатами Nova и Placement, расчёт пула Cinder и назначение object ring описаны независимо друг от друга. Для эксплуатационных команд RabbitMQ, OVS и libvirt приведена документация их разработчиков. Она не привязана к версии OpenStack, поэтому параметры сверяют с поставленной версией. Команды для сбора свидетельств

Примеры сбора сведений без изменения конфигурации. Имена облачного профиля и сервиса заменяют на локальные. Используйте профиль аудитора с правами чтения соответствующих API. Имя файла TLS-ключа ниже относится только к сертификату тестового клиента. В качестве URL укажите согласованный маршрут чтения, на котором действует проверяемый профиль mTLS.

openstack --os-cloud auditor endpoint list --service identity
openstack --os-cloud auditor domain list
openstack --os-cloud auditor role assignment list --user "$TEST_USER_ID" --names --effective
ss -lnt
getent ahosts "$PUBLIC_FQDN"
chronyc tracking
chronyc -n sources -v
sudo auditctl -s
sudo auditctl -l
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  --cacert "$SERVER_CA" --cert "$TEST_CERT" --key "$TEST_KEY" "$TEST_URL"
curl --silent --show-error --output /dev/null --write-out '%{http_code}\n' \
  --cacert "$SERVER_CA" "$TEST_URL"

Успешная TLS-проверка и успешная авторизация на прикладном уровне — разные наблюдения. Для R9 зафиксируйте отдельно статус TLS, код HTTP, если он получен, и решение публичного шлюза. Код 000 у curl означает, что клиент не получил HTTP-ответа. Причину уточняют по коду завершения и журналу шлюза. Для R49 чтение конкретного файла можно зарегистрировать без вывода его содержимого, например sudo head -c 1 "$CONFIG_PATH" > /dev/null; запись ищут по штатному изменению, уже проведённому в том же наблюдаемом расположении. chrony — команды мониторинга · Red Hat Enterprise Linux 9 — Linux Audit
